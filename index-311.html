Step 1 — OpenSpec: AI 에이전트용 컨텍스트 설계

왜 필요한가

LLM은 맥락 없으면 엉뚱한 코드를 냅니다. Cursor, Jules, opencode를 같은 프로젝트에서 섞어 쓸 때 공통 사전 지식(project.md)을 미리 선언해두면 매번 스택 설명을 반복하지 않아도 됩니다.

openspec/project.md
스택, 컨벤션, 도메인 용어 기술
openspec/changes/[id]/proposal.md
기능 단위 변경 제안서
openspec/changes/[id]/specs/[cap]/spec.md
SHALL/MUST 기반 요구 명세
openspec validate [id] --strict
명세 검증 및 누락 항목 탐지
npx openspec init
openspec validate add-user-score --strict

project.md 작성 예시

## Tech Stack
- Framework: Next.js 16 (App Router, Server Components 우선)
- ORM: Prisma (migration 파일로 변경 이력 관리)
- Database: Supabase (PostgreSQL + RLS)
- Auth: Supabase Auth (Google OAuth)
- Deploy: Vercel (main → production, feature/* → preview)

## Conventions
- 컴포넌트: src/components/
- API Route: app/api/ (Route Handlers)
- 환경 변수: vercel env pull로 .env.local 자동 동기화
Design Principle

AI 에이전트는 "좋은 프롬프트"보다 "좋은 컨텍스트"에 더 잘 반응합니다. project.md가 모든 에이전트의 온보딩 문서 역할을 하는 셈입니다.

Tip — project.md를 영문 압축형으로 작성하는 이유

project.md는 매 요청마다 컨텍스트 윈도우에 통째로 들어갑니다. 한국어 설명체로 쓰면 토큰이 4배 가까이 소비되고, LLM 파싱 품질도 오히려 떨어집니다.

Before — 설명체

## 기술 스택
이 프로젝트는 Next.js 16의 App Router를 사용하며,
데이터베이스는 Supabase의 PostgreSQL을 활용합니다.
ORM으로는 Prisma를 사용하고 있으며, 마이그레이션
파일로 스키마 변경 이력을 관리합니다.

RLS (Row Level Security) 개념

RLS는 PostgreSQL의 행 단위 접근 제어 기능입니다. API 레이어에서 필터를 빠뜨려도 DB에서 막아줍니다. 보안을 이중으로 걸어두는 방식입니다.

구분API 레이어 필터RLS (DB 레이어)
적용 위치애플리케이션 코드데이터베이스 정책
우회 가능성버그 시 데이터 노출 위험우회 불가 (DB 레벨 강제)
설정 방법WHERE 절, 미들웨어CREATE POLICY 구문

Prisma 스키마 및 Connection Pooling

// prisma/schema.prisma
datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")   // PgBouncer 경유 (Vercel 런타임)
  directUrl = env("DIRECT_URL")     // 직접 연결 (migration 전용)
}

model GameScore {
  id        String   @id @default(cuid())
  userId    String
  gameName  String
  score     Int
  createdAt DateTime @default(now())

  user User @relation(fields: [userId], references: [id])
  @@index([gameName, score(sort: Desc)])
}
Connection Pooling 분리 이유

Vercel 서버리스는 요청마다 새 커넥션을 만들어서 금방 DB 연결 한도에 걸립니다. PgBouncer가 커넥션을 재사용해주므로 이 문제를 피할 수 있습니다.

npx prisma migrate dev --name add-game-score

Step 3 — Vercel CLI: CI/CD 파이프라인 연결

대시보드 없이 터미널에서 환경 변수 동기화 → 빌드 → 배포까지 끝낼 수 있습니다. Jules가 올린 PR에는 Vercel 프리뷰 URL이 자동으로 붙어서 모바일에서 바로 확인할 수 있습니다.

npm install -g vercel
vercel link                    # 로컬 프로젝트 ↔ Vercel 프로젝트 연결
vercel env pull .env.local     # 프로덕션 환경 변수를 로컬에 동기화
vercel deploy                  # 프리뷰 배포 (브랜치 URL 생성)
vercel --prod                  # 프로덕션 즉시 배포

브랜치 전략과 배포 환경 매핑

브랜치배포 환경URL 패턴
mainProductionmyapp.vercel.app
feature/*Previewmyapp-git-feature-xxx.vercel.app
Pull RequestPreviewPR 본문에 URL 자동 삽입

Jules가 PR을 올리면 Vercel이 Preview URL을 자동으로 붙여줍니다. 지하철에서 스마트폰으로 확인하고 Merge하면 끝입니다.

Step 4 — 로컬 AI 코딩: opencode + Copilot Agent

도구실행 환경강점
opencode터미널 / CLISSH 환경, 에디터 없는 서버에서도 동작
Copilot AgentVS Code 내파일 직접 편집, 멀티 파일 동시 생성

둘 다 openspec/project.md를 컨텍스트로 넘기면 프로젝트 컨벤션을 이미 아는 상태로 작동합니다. opencode는 터미널·SSH 환경에서, Copilot Agent / Cursor는 VS Code 안에서 동일한 방식으로 사용합니다.

Supabase RLS 정책 — 보안 설계 관점

-- 인증된 사용자만 자신의 점수를 INSERT 가능
CREATE POLICY "insert_own_scores"
  ON public.game_scores FOR INSERT
  WITH CHECK (auth.uid() = user_id);

-- 랭킹 조회는 전체 공개 (SELECT)
CREATE POLICY "read_all_scores"
  ON public.game_scores FOR SELECT
  USING (true);

"보안 신경 써"라고 매번 지시하는 대신, 컨텍스트에 넣어두면 에이전트가 알아서 포함시킵니다.

사내에서도 쓸 수 있을까 — 금융권 관점에서 생각해보면

저도 처음엔 "전금법 때문에 어차피 못 쓰겠다"고 생각했습니다. 그런데 막히는 건 외부 서버에 코드를 보내는 행위이지, 이 개발 흐름 자체가 아닙니다. 구성 요소만 사내 것으로 바꾸면 됩니다.

코드가 외부 서버로 나가는 게 문제입니다. 에이전트가 사내망 안에서 돌면 됩니다.

Jules의 모든 기능을 한 번에 구현하는 건 현실적이지 않습니다. 구현 난이도와 인프라 준비 정도에 따라 단계를 나눠보면 이렇습니다.

MVP — 일단 이것부터

인프라 부담 없이 가장 빠르게 "에이전트가 MR을 올려준다"는 경험을 만들 수 있는 최소 구성입니다.

① GitLab 웹훅
Issue에 특정 라벨 부착 → 에이전트 서버로 페이로드 전송. 추가 인프라 없이 GitLab 설정만으로 가능.
② 에이전트 서버 (사내망)
웹훅 수신 → 저장소 클론 → LLM 호출 → 코드 수정 → MR 생성. Python + opencode CLI로 구성 가능.
③ LLM — 일단 외부 API
코드가 외부로 나가지 않는 선에서 API 게이트웨이 경유도 고려 가능. GPU 서버 준비되면 Ollama로 교체.
④ MR + 사내 CD
에이전트가 올린 MR → 기존 Jenkins/ArgoCD 파이프라인 그대로 타면 됨. CD 변경 없음.

요점

GPU 없어도 됩니다. 외부 LLM API를 게이트웨이로 감싸거나, 코드를 직접 보내지 않는 방식(diff만 전송)으로 우선 시작할 수 있습니다. MR이 자동으로 올라오는 경험 자체를 먼저 만드는 게 목표입니다.

개발자 → AI 에이전트에게 지시 → 에이전트가 PR 생성 → 개발자가 검토 후 Merge → 자동 배포

Jules 시연 — 단계별 흐름

시연 순서

Jules 대시보드 확인 → 웹에서 새 세션 생성 → GitHub Issue 라벨 방식 → 모바일 지시 → PR·배포 연결 확인

STEP 1 — jules.google.com: 대시보드에서 진행 중인 작업 확인

Jules에 접속하면 저장소별로 현재 실행 중·완료된 세션 목록이 보입니다. 각 세션은 어떤 파일을 수정했는지, 서브태스크가 어디까지 진행됐는지 실시간으로 표시됩니다.

상태표시 내용
🟡 In Progress현재 수정 중인 파일 목록, 서브태스크 진행 단계
✅ Completed생성된 PR 링크, 변경된 파일 수, diff 요약
❌ Failed실패 원인 로그, CI Fixer 자동 재시도 여부

CLI에서도 동일하게 확인할 수 있습니다.

# 현재 저장소의 모든 세션 조회
jules remote list --repo

# 출력 예시
SESSION ID   STATUS       TITLE                        PR
sess_a1b2    completed    랭킹 1~3위 배경색 적용        #31
sess_c3d4    in_progress  닉네임 컬럼 추가              -
sess_e5f6    completed    npm audit fix (scheduled)    #29

jules.google.com에서 저장소를 선택하고 지시를 입력하면 Google 클라우드 샌드박스에서 즉시 실행됩니다. 로컬 PC가 꺼져 있어도 무관합니다.

STEP 3 — GitHub Issue에 jules 라벨 → 자동 작업 지시

Issue를 별도로 Jules에 전달할 필요가 없습니다. 이슈에 jules 라벨만 붙이면 Jules가 이슈 본문을 읽고 스스로 세션을 시작합니다. 팀원이 이슈를 등록하고 라벨만 붙여도 작업이 시작됩니다.

// GitHub Issue #34 예시
Title : [feat] 게임 종료 후 공유 버튼 추가
Label : jules, enhancement

Body :
게임 결과 화면 하단에 카카오톡 공유 버튼 추가
- /app/game/result/page.tsx
- kakao SDK는 이미 설치되어 있음 (lib/kakao.ts 참고)
- 공유 텍스트: "나는 {score}점! 도전해봐 → {url}"

이슈 등록자가 개발자일 필요도 없습니다. 기획자·QA가 이슈를 쓰고 라벨을 붙이면, Jules가 코드로 구현해 PR을 올립니다.

STEP 4 — 모바일에서 지시 → 작업 진행 중 확인

STEP 5 — PR → Vercel 배포 연결 확인

Jules가 올린 PR에는 Vercel 봇이 프리뷰 URL을 자동으로 댓글로 첨부합니다. Approve 하는 순간 main 브랜치에 머지되고, Vercel이 프로덕션 빌드를 자동으로 시작합니다.

단계자동 처리 내용개발자 액션
PR 생성Vercel Preview 빌드 시작—
PR 본문Preview URL 자동 첨부모바일로 UI 확인
CI 통과lint / type-check / build 자동 실행—
Approve + MergeProduction 빌드 자동 시작Approve 버튼 클릭
배포 완료Slack / GitHub 알림 발송—

개발자가 직접 하는 것은 PR diff 읽기 → Approve 클릭 두 가지뿐입니다. 나머지는 모두 자동입니다.
